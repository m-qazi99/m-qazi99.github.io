Investigating pipeline failures with dependency graphs

A reproducible walkthrough of failure propagation, retries, recovery coverage, and completion targets in Pipeline Pulse.

By Muzammil Qazi · Published 2026-10-20 · Independent portfolio demonstration

Start with dependencies, not the loudest error

A failed pipeline activity can stop several downstream assets. Treating each blocked activity as a separate root cause wastes effort. First identify the activity that failed, then trace which downstream activities depend on it.

Pipeline Pulse demonstrates this with a synthetic sales pipeline. Its default definition includes CRM and billing sources, landing activities, a quality gate, a sales transformation, two marts, a dashboard, and an export. None of these represent an employer system.

A reproducible example

In the public sample, an injected fault affects transform. With three workers, one allowed retry, and five seconds of initial backoff, the simulator completes seven of twelve activities. Four downstream activities are blocked. The failed scenario stops at 205 simulated seconds; repairing the selected transformation in the recovery comparison completes all twelve activities in 191 seconds.

These numbers describe this synthetic input and scheduling policy only. Reproduce them with the versioned example input and inspect the Python simulator.

Retries and repairs answer different questions

A bounded retry may recover a transient fault if a later attempt succeeds. It still consumes activity time, and backoff counts against the completion target. Repairing a modeled persistent cause is a different experiment: the recovery comparison removes failures from the selected activity. It does not execute a real operational change.

The simulator holds a worker slot during retry backoff. This explicit simplification matters when comparing worker budgets; a production orchestrator may use different scheduling behavior.

Measure coverage before celebrating speed

A failed run can appear faster because it skips blocked work. Compare completed activities and failed or blocked assets before comparing elapsed time. A short run with an incomplete dashboard is not a successful recovery.

The capacity planner tests worker budgets from one through eight under the same graph, retry policy, and selected repair. It recommends the smallest tested budget that completes every activity within the chosen target. Its utilization figure excludes backoff and is not a cloud billing estimate.

Use the graph as an investigation aid

  1. Keep the source definition and business dependency relationships intact.
  2. Identify the failing activity and trace its downstream impact.
  3. Test whether retry policy or a modeled repair restores full completion.
  4. Compare completion targets and resource budgets under the same assumptions.
  5. Retain the input and result as evidence so another person can reproduce the experiment.

Try the incident arena or inspect the tests. The exercise grades deterministic conditions; it is not an assessment of a live incident or proof of production reliability.
