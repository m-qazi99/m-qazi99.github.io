How to evaluate lexical runbook retrieval

Inspect BM25 and TF-IDF search with labeled queries, reciprocal rank, Hit@K, chunking controls, and source passages in Runbook Radar.

By Muzammil Qazi · Published 2026-10-20 · Independent portfolio demonstration

Evaluate the source passage before the answer

A search interface can appear helpful while returning an irrelevant passage. Before adding a generated answer, inspect whether the retrieval step finds useful source evidence. Runbook Radar isolates that step: it compares BM25 with TF-IDF cosine similarity and returns passages from supplied Markdown notes.

The public project is lexical search, not a generative assistant. It does not call an LLM, use embeddings, or determine whether operational instructions are correct.

Keep a labeled query set separate from the demo query

The versioned synthetic example contains runbook headings and four labeled queries. Each label specifies the expected document title. The query “watermark missing records” expects “Missing records and watermark gaps”. Inspect the returned passage as well as the title: a title-level hit can still contain insufficient context.

Use varied phrasing and keep some queries out of the tuning loop. Include questions that the corpus cannot answer. A tiny synthetic set can validate a calculation or illustrate a tradeoff; it cannot establish general retrieval quality.

What do MRR and Hit@K measure here?

For each labeled query, the engine finds the first positive-scoring chunk whose title matches the expected document. Reciprocal rank is one divided by that rank; it is zero when there is no matching result. Mean reciprocal rank averages those values across the supplied questions.

Expected-title ranks: 1, 2, no match, 4
MRR = (1 + 1/2 + 0 + 1/4) / 4 = 0.4375
Hit@3 = (1 + 1 + 0 + 0) / 4 = 0.5

These ranks are an illustrative calculation, not a measured benchmark from the app. The implementation rounds aggregate scores to three decimal places. Its MRR uses the full positive-scoring ranking; Hit@K applies the chosen K cutoff. It evaluates document-title labels against a chunk ranking, so several chunks from one title can affect the rank positions.

Change chunking as a controlled experiment

Runbook Radar splits each Markdown document into word windows. The studio accepts 30–300 words per chunk, overlap smaller than the chunk size, and K from 1–10. Larger overlap repeats context and increases the chunk count. It also changes the corpus statistics used by the scorers, so a score from one chunk configuration is not directly comparable with a score from another.

Keep the documents and labeled questions fixed while changing one control. Compare the first relevant rank, source coverage, and failure cases. The tool exposes term contributions so you can see which shared words raised a passage in the ranking.

A retrieval score is not confidence

BM25 ranks shared terms with frequency saturation and length normalization. TF-IDF uses weighted term vectors and cosine similarity. Neither score is a probability that a passage is correct, current, safe, or relevant to a particular production system. The implementation retains only positive-scoring matches; a query with no lexical match produces an empty result rather than fabricated evidence.

Reproduce and review

  1. Load the synthetic studio example in the live Python application.
  2. Run both retrieval methods with the same chunk size, overlap, query set, and K.
  3. Inspect the passages, matching terms, and expected-title ranks.
  4. Export the experiment JSON to keep the inputs, scores, and evaluation context together.
